# Photoshop 核心条目逐条清单（190 条）

> 目的：把 `docs/ps-parity.md` 里口径 D/C 的分母与命中数变成**可复算**的。
> 上一版（2026-10-23～10-27）只有九维配额与一个估计的命中总数，没有任何逐条清单，
> 导致「命中 118/190」无法被复核——任何人换几个缺口项就能把总分调到 78%～85%。
> 本清单是那次批评的收口：**每条一行，标命中与否，并给出可 grep 的证据**。
>
> 维护规则：新增能力时只改对应行的「命中」与「证据」两列，**不改条目本身**；
> 要增删条目属于改分母，须单独说明。`scripts/check_docs.py` 会校验
> 「本文件条目总数 == 190」且「各维命中数 == ps-parity.md 表格声明值」。

## 0. 判定口径（读表前先看这四条）

| 规则 | 内容 |
|------|------|
| **R1 一条是什么** | 「用户能直接触发的一个功能动作」。变体不重复计：24 种混合模式算 1 条「混合模式」，25 种调整算 1 条「调整层」，16 种滤镜算 1 条「滤镜菜单」。 |
| **R2 命中的门槛** | 必须有**用户可达的入口**（菜单项 / 快捷键 / 面板）且**后端真的实现**。只有 ABI 没有 UI 入口的，记「部分」并在证据列写明缺哪一半；「部分」在计分时按**未命中**处理（保守）。 |
| **R3 证据怎么写** | 写可 grep 的符号（ABI 名、`kCmd*`、函数名、文件路径）。写不出证据的一律记未命中。 |
| **R4 ML 与外部解码器** | 依赖 ML 模型（Select Subject / Remove Background / Neural Filters）与需第三方解码器的格式（HEIF/WebP/TIFF/RAW），按 `BACKLOG.md` §5 计未命中，不设豁免。 |

**状态标记**：`✅ 命中` ／ `◐ 部分`（有实现但缺入口或缺变体，计未命中）／ `❌ 未命中`。

① 早版把 9 项已落地能力仍记在缺口；② 逐条枚举后发现多维度估低；③ 复合条目被拆开。
三次都往**更严**的方向走，现在 78% 是这份清单能给的最保守数字。

## 12. 口径 C 的「日常子集」——逐条点名（117 项）

### 12.0.1 「日常」怎么定义（去掉主观，改成频率分档）

上一版我直接给每项判「日常/非日常」，这是凭感觉。现在改为**先定分档，再按档纳入**：

| 档 | 判定标准 | 是否进日常子集 |
|---|---|---|
| **A 每次开图必用** | 打开/保存/关闭、图层基础、选框与画笔、撤销重做 | ✅ 进 |
| **B 一周内大概率用到** | 图层样式、调整层、常用滤镜（锐化/模糊/降噪）、文字基础、缩放视图 | ✅ 进 |
| **C 特定任务才用** | Warp 变形、快速选择、压感、色板、蒙尘划痕、粗体斜体、背景橡皮擦、图层对齐 | ✅ 进（这几项是"做某类图必然碰到"，不是锦上添花） |
| **D 偶发/专业向** | TIFF/WebP/RAW/PDF 导入导出、CMYK/ICC/软打样、打印、模糊画廊、扭曲/像素化/风格化/渲染、批处理与脚本 | ❌ 不进 |
| **E 本仓明确的非目标** | ML 类（Select Subject）、3D/视频、云端协作 | ❌ 不进（BACKLOG §5） |

**C 档为什么纳入**：这些是"做某类活就必然要用"的能力（做海报要 Warp、做标题要粗体、
用数位板要压感）。排除它们会让日常口径虚高。**8 个 ⚠️ 缺项全部落在这档**——
也就是说：**日常口径的缺口，全部是「特定任务型」能力，不是"偶尔用用"的东西。**

**这套分档仍然含判断**（比如「色板算 C 档还是 D 档」可以争），但比逐项拍脑袋强的地方在于：
**每项都落到某一档，档的边界写在上面，读者可以按档重算**。若把某档整体挪进/挪出，
数字会变，但变化量可以算（每项 ≈ 1/117 × 权重）。

1. **档的边界是判断。** 缓解办法：8 个缺项全部列出、档的定义写在 12.0.1，可按档重算。
2. **93% 只代表「能力存在」，不代表「好用」。** 面板能不能开、快捷键顺不顺、
   参数调起来麻不麻烦——这些**一个字都没算进去**。交互质量只有
   `docs/manual-test.md` 的人工目视能回答。**93% ≠ 用起来有 PS 的 93% 顺。**

#### 13.0.1 级别判定规则（机械可算，不留主观空间）

上一版我给每条缺口标 S/M/L 是**凭经验判断**，同一类活还给了两种级别（P16 画笔动态
标 L 用 3,341 行锚点、P15 压感标 S–M 用 669 行锚点，两条都在「画笔」范畴）。
已改为下面的规则，任何人可以重算：

| 级别 | 判定条件（全部满足） | 区间来源 |
|---|---|---|
| **S** | 无新领域模型、无新 ABI 导出（最多追加枚举值或结构体尾字段）、单一入口 | 先例 `b765066` 461 / `1e2300b` 669 |
| **M** | 无新领域模型，但需要 ≥1 个新 ABI 导出**或**新增一块面板 | 先例 `d623d18` 1,027 / `a9a080a` 1,454 / `ee0cad9` 1,744 |
| **L** | 需要**新的领域模型**（进 `DocumentState`、进 `.comp`、或多处消费点同步改） | 先例 `e852cd8` 2,017 / `0d372ed` 2,260 / `6da55fd` 3,341 |
| **XL** | 需要**引入第三方库**或**独立子系统**（打印/色彩管理/脚本引擎） | 无先例，只给下限 |

**同一个缺口族拆多个子项时，规模按族计**（不再逐条给不同级别）。例如：
- `P16` 画笔动态/纹理/间距 = 1 个族（L，多次改 `comp_tool_brush` 与笔尖采样）
- `P15` WinTab 压感 = 1 个族（M，壳层输入 + 逐 dab 采样，无新模型）
- `A40–A44` 五个滤镜族 = 5 个族（每个 L，因为每个都是 4–6 个独立算子）
- `A45` + `A46` = 1 个族（S，纯枚举追加 + 复用卷积框架）

#### 13.0.2 三条仍然成立的局限（删不掉，只能声明）

1. **这是「规模外推」，不是「工期」。** 本仓 git 时间戳不可用（同批提交时间完全相同），
   无法反推工时。**任何"要几天"的说法都缺依据**，本文件不提供天数。
2. **XL 项无先例。** 下限按最近 L 项（3,341 行）计，实际很可能远超——色彩管理、
   打印、脚本引擎都是本仓从未涉足的子系统。
3. **含第三方库的项，规模不在行数而在决策。** TIFF/WebP/HEIF/RAW/PDF 与「零依赖自研」
   取向冲突，会先卡一次「引不引库」的决策；定了才谈实现。
